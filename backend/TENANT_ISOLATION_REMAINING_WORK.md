# Tenant isolation — remaining work

Tracks progress against the audit's finding that 38 of 58 backend route files had zero `businessId` scoping. This file exists so the remaining gap is recorded precisely rather than silently left implicit — per the Trust Release directive, "record the exact blocker and continue."

## Fixed in this pass

| File | What was fixed |
|---|---|
| `middleware/actor_context.py` | The root cause: `ActorContextMiddleware` let a client-supplied `X-Tenant-Id`/`X-Business-Id` header override the JWT-derived businessId. JWT membership is now authoritative; the header is only consulted when there's no JWT at all (the original partner-integration use case). |
| `routes/commerce_v29.py` | Voucher creation no longer trusts a client-supplied `businessId` in the request body over the authenticated caller's own. |
| `routes/kitchen.py` + `models/kitchen_order.py` | Added `businessId` to the `KitchenOrder` model; every read/write endpoint (list, create, start/ready/served/cancel, hold/fire/ready/serve-course, timings, priority, prep-list) now scopes or stamps by it. `fire_course_internal` takes an optional `business_id` used by both the HTTP route and the scheduler/auto-fire callers (`services/coursing_scheduler.py`, `routes/coursing.py`). |
| `routes/payroll.py` | `calculate_payrun`/`commit_payrun`/`payroll_register`/`payroll_ytd`/`payslip_pdf`/`roster_compliance` all scoped — previously a payroll run for one business pulled in *every* business's active staff and wages. `timecards`/`shifts` don't carry their own `businessId` (schema gap, see below) so those are filtered transitively through this business's own staff list; `payruns`/`payrun_rows` now get `businessId` stamped going forward. |
| `routes/gamification.py` | `compute_staff_performance` (leaderboard), `smart_distribute_tips`, `quarterly_review` all scoped — same "one tenant's data mixed into another's" pattern as payroll, now fixed the same way. |
| `routes/finalize.py` (partial) | Customer wallet lookups (`guest_wallet`, `lookup_by_token`, `_resolve_wallet_context` → Apple/Google wallet passes) were the highest-risk finding in this file — any authenticated staff member of *any* business could pull *any* customer's name/points/store-credit balance by customer_id with no ownership check. Fixed. `preshift_briefing`'s product/promotion/roster/timecard queries also scoped. |
| `routes/bill_split.py` | **A more severe finding than tenant scoping**: `active-splits`, `staff-status` and `staff-process-tab` had *no authentication at all* — this whole router rides server.py's `/api/table/` public prefix (meant for the genuinely guest-facing split/claim/checkout endpoints in the same file), and the prefix match doesn't distinguish "guest-facing" from "staff-only". Note: `db.bill_splits` itself still carries no `businessId`/venue field at all (a `tableNumber` can collide across two different businesses' open splits on a shared deployment) — auth is fixed, cross-tenant-staff scoping for this collection is not; see the schema-gap note below. |
| `routes/identity.py` + `services/customer_identity.py` | `identity_customers` already had a `venue_id` field, just never wired to anything real — every caller left it at the hardcoded default `"main"`, so every business's guest identities shared one venue and any staff member of any business could search or read any other business's identity records (`search_identity`, `get_identity`, `segment_preview`, `migrate_legacy_crm`). `venue_id` is now threaded from the caller's real `businessId`; `"main"` is treated as the legacy/untagged sentinel for backward compatibility, same shape as `tenant_scope_filter`'s own missing-field handling. `guest_profiles`/`loyalty_accounts`/`punch_cards` weren't touched directly — they're keyed only by `customer_id` (an FK into the now-scoped `identity_customers`), so scoping the parent record is sufficient; a caller can't reach a child record without first discovering its `customer_id` through an already-scoped parent lookup. |
| `routes/reservation_features.py` | Zero businessId scoping across `table_combinations`, `booking_shifts`, `booking_experiences`, `club_offers`/`club_claims`, `social_accounts`, and `email_log`. **`social_accounts` is the sharpest finding**: it stores real OAuth `accessToken`s for a business's connected social media accounts — any owner of any business could list every other business's connected accounts, tokens included, and had no scoping check on delete either. All scoped now; guest-reachable reads (`booking/experiences`, `clubmember/offers`) use `optional_user` so a genuinely anonymous guest still gets the prior unscoped-for-guests behavior (not worse than before) while a logged-in staff caller is scoped to their own business. `db.settings` keys `booking_rules` and `email_config` deliberately left global — same singleton-settings architectural gap as `business_settings`/`print_routing`, not fixed here for the same reason. |
| `services/notification_service.py` + `routes/notifications.py` (not on the original list — the shared notification bell, used by 6 other route files) | **Systemic cross-tenant leak, found while auditing `notifications.py`.** Role/topic-broadcast notifications (`send(role="owner", ...)` for critical pulse alerts, `send(role="marketing", ...)` for loyalty milestones/referrals, `send(role="server", topic="kitchen.ready", ...)` for kitchen pings — 8 call sites across `analytics.py`, `kitchen.py`, `loyalty_v2.py`, `nua.py`, `table_courses.py`) carried no `businessId` at all. A role broadcast isn't tied to any business, so **every account sharing that role across every business on the deployment saw it** — an owner of Business A saw Business B's critical alerts, kitchen "order ready" pings, and marketing notifications, with no way to tell they weren't their own. Fixed at the root in `send()`: when a caller doesn't pass `business_id` explicitly (none of the 8 existing call sites do), it now defaults to the current request's actor context — this fixes every existing call site automatically rather than requiring 8 separate edits, since each one already runs inside a request that has that context populated. `list_for`/`mark_all_read`/`unread_count` scope role-matched conditions by the same logic; email-targeted notifications were already implicitly safe (an email belongs to one business's staff account) and weren't touched. |
| `routes/loyalty.py` | Several endpoints (`update_loyalty_reward`, and the whole events CRUD — `get_events`/`create_event`/`update_event`/`book_event_ticket`) had **no auth dependency at all**: any valid staff token, any business, could modify another business's reward pricing or create/edit/book any business's events. Zero businessId scoping across `loyalty_rewards`, `loyalty_tiers`, and `events` on top of that. All fixed. `loyalty_tiers`' seeded defaults use fixed, non-unique ids (`"tier-bronze"` etc. — a literal shared across every business), so `businessId` is what actually keeps two businesses' seeded copies from colliding on the same document once each has seeded their own; the update endpoint now scopes its lookup accordingly. |
| `routes/channel_menus.py` | Zero businessId scoping across all 4 collections it touches (`products`, `channel_menus`, `kds_orders`, `transactions`) — any business's channel-pricing overrides, AI prep-time sync, and AI slow-mover discounts could read and write against every other business's product catalogue. `GET /channels` and `GET /{channel}` also had no `Depends` at all (any valid token, no role check). All 8 endpoints scoped/authed now. `kds_orders` appears to be dead code (no other reference anywhere in the codebase writes to it) — scoped it anyway for consistency, but it's a no-op either way. |
| `routes/hq.py` | Explicitly a cross-location feature by design (franchise/brand roll-ups via `businesses.parentBrandId`) — but none of its 4 endpoints ever checked which brand a location belonged to. `/kpi-roll-up` and `/leaderboard` aggregated `db.transactions` across literally every business on the deployment with no filter at all, so any logged-in staff member could see every *unrelated* tenant's revenue, covers, and GST, not just sibling locations under their own brand. `/brands` and `/locations` had the same gap for the business directory itself. Fixed with `_brand_scope_business_ids()`, which resolves the caller's own brand root plus every location under it, and scopes all four endpoints to that set — this is the one file in this pass where the fix is deliberately NOT the usual single-business `tenant_scope_filter` pattern, since the feature's entire purpose is seeing *multiple* locations, just only the caller's own group of them. |
| `routes/reservations.py` (floor-plans section only) | **Not one of the audit's original 34 files** (this file was presumably assessed as already-scoped) — found while investigating whether `table_courses.py`'s `table_states` collision risk extended to floor-plan table ids. It did, and worse: `GET/POST/PUT/DELETE /floor-plans`, `/floor-plans/tables/{id}/status`, and `/floor-plans/sections/{id}/assign` had **no `Depends` at all** on most of these endpoints (the global auth middleware still required *some* valid token since this path isn't in the public allowlist, but no role or ownership check beyond that) and zero businessId scoping — any staff member of any role or business could create, view, modify, or delete any other business's entire floor plan. Fixed: `get_user` for reads, `require_owner_or_manager` for writes, `businessId` stamped/scoped throughout. `services/floor_tables.py` (the shared resolve-a-typed-table-number service used by the POS, kitchen coursing, table pacing, and table_ordering.py's QR flow) was **not** touched — threading `business_id` through it and its many call sites is a real, separate, larger piece of work, deliberately deferred rather than rushed; table ids there are 8-hex-char UUID-style strings (`TBL-XXXXXXXX`), so the practical collision risk is much lower than the raw-tableNumber collisions this pass fixed elsewhere, but the underlying cross-tenant visibility gap is still real. |
| `routes/table_courses.py` | `table_states` (live floor-plan seating/course state) and `dock_notifications` (the "Send" nudge log) were keyed with no `businessId` at all — worse than a read leak: `table_states` is looked up only by `tableId`, so two businesses on a shared deployment both seating "Table 5" collided on one document (one business's course/guest-name/VIP data could be silently overwritten by the other seating a same-numbered table, and one clearing their table could clear the other's). Both scoped now; `table_course_settings` (a `_id: "singleton"` doc) deliberately left global, same architectural gap as `business_settings`. `services/table_pacing.py` and `services/ticket_lifecycle.py` also touch `table_states` directly by a resolved internal floor-plan table id (not the raw client-supplied `tableId` string this fix addresses) — plausibly already collision-safe since that id is resolved through `floor_tables.resolve_table()`, which is presumably itself business-scoped, but this wasn't independently verified and is worth confirming in a future pass. |
| `routes/awards.py` | Another zero-auth finding, and a compliance-sensitive one: all 6 endpoints (`catalogue`, `install`, `installed`, `uninstall`, `sync-fairwork`, `payruns/super-by-award`) had no `Depends` at all — any authenticated user of any role/business could install or uninstall Fair Work awards, and `db.awards` was keyed only by `code` (e.g. `"MA000119"`, a shared national identifier), so two businesses installing the same award collided on one document — business A uninstalling it silently uninstalled it for business B too. Auth added (`require_owner_or_manager` for install/uninstall/sync, `get_user` for reads); `db.awards` re-keyed to `(code, businessId)` so each business's install state is independent. |
| `services/entity_service.py` (root cause) + `routes/measured_inventory.py` | **The single highest-impact fix in this whole pass.** `_stamp_new()` used `doc.setdefault("businessId", ctx.get("businessId"))` — but every `BaseEntity`-derived model (and `Product` specifically) declares `businessId` as a real field defaulting to `None`, so a caller that builds a full model instance and passes `model.dict()` into `stamped_insert` already has an explicit `"businessId": None` key. `setdefault` is a no-op against an *existing* key, even a `None` one, so the actor's real businessId was never applied. Confirmed victim: `routes/products.py`'s `create_product` — **every product ever created via `POST /api/products` was stamped with `businessId=None`, regardless of who created it**, making every business's entire product catalogue (cost, stock, pricing) universally visible to every other business through `tenant_scope_filter`'s "missing/null = visible to everyone" backward-compat default. `services/menu_features.py`'s bulk-import and `services/alcohol_seeder.py`'s seeding write "products" through the same path and were equally affected. Fixed at the root: `_stamp_new` now overwrites a falsy `businessId`/`locationId` instead of only filling in a missing key — this fixes every current and future caller of `stamped_insert`, not just products. `routes/measured_inventory.py` (11 endpoints across `stock_units`/`sell_variants`/`open_containers`/`wastage_events`) was scoped transitively through `db.products` at the same time — those four collections' own writes were NOT hit by the `_stamp_new` bug (their `...Create` request models have no `businessId` field, so the key was genuinely absent, not explicit-`None`), but nothing had ever filtered a *read* by tenant either, so margin/cost/wastage data was fully cross-tenant readable regardless. |

## A completed systematic sweep for the same bug class (missing `Depends` entirely)

A regex scan across every route in the 30 remaining files for a signature with no `Depends(...)` anywhere in it turned up ~65 matches. Triaged all of them:

- The large majority are legitimately public by design — under a `PUBLIC_API_PREFIXES`/`PUBLIC_API_PATHS` entry (guest storefront, kiosk, QR table ordering, webhooks with their own signature verification, health checks) — consistent with their own naming/docstrings.
- `routes/repo_sync.py`'s `/status` and `/run` are a **false positive of the scan method**: they auth manually inside the function body (`get_current_user(request)` + an owner-only role check) rather than via a `Depends(...)` in the signature, which the regex can't see. No issue.
- `routes/licensing.py`'s `/validate` is not in the public allowlist, so the global `RequireAuthMiddleware` already requires a valid staff token to reach it — the opposite problem from a security gap: its own docstring says it's meant to be called by a POS device *before* anyone has logged in, so it may currently be *non-functional* for that bootstrap case rather than insecure. A functional bug, not a vulnerability — flagged here, not fixed (out of scope for this security pass).
- No other instance of the true "reachable with zero credential at all" bug class (the `bill_split.py`/`awards.py` pattern) was found in this sweep. The remaining ~15 matches not covered above are routes that DO require a valid staff token via the global middleware but have no *route-level* role/tenant check beyond that (e.g. `advanced_features.py`'s `/tips/add`, `bookings_inbox.py`'s ingest/ack/dismiss, `channel_menus.py`, `loyalty.py`'s rewards/events, `reservation_features.py`'s table-combinations/schedule/club-offers, `v25_suite.py`'s sync-queue/hardware-heartbeat/dynamic-pricing/subscriptions) — lower severity than a true zero-auth gap (an attacker needs SOME valid staff credential, not none at all), but still worth the normal tenant-scoping pass each of these files needs regardless, per the recommended order above.

**Worth a dedicated follow-up, not scoped here:** now that `_stamp_new`'s root-cause businessId bug is fixed, it's worth grepping the codebase for every model that extends `BaseEntity` (or otherwise declares an explicit `businessId: Optional[str] = None` field) and is constructed as a full model instance before being passed to `stamped_insert`, to confirm `products` was the only *currently-read* collection affected — `menu_features.py` and `alcohol_seeder.py` both write "products" through the same bug and are already covered by the fix, but a systematic check would catch any other collection with the same construction pattern that this pass didn't specifically go looking for.

## RESOLVED, post-P0.3 — `routes/loyalty_v2.py` ("Loyalty 2.0"), not one of the original 34, found during Phase 3-5 feature work

Discovered while building a unified guest-facing loyalty passport (folding subscription/membership status into the existing points/tier/badges/milestones guest view) — a genuinely severe, previously-undiscovered gap on par with the `_stamp_new` root-cause bug and the `accounting_service.py` finding. **Zero businessId scoping anywhere** in this file:

- The badge and milestone catalogs seeded once globally (`if collection.count_documents({}) == 0`) — every business after the very first one to ever trigger seeding saw the catalog as already non-empty and got no catalog of its own. - `GET /progress/{customer_id}` and `POST /evaluate/{customer_id}` had **no ownership check at all** — any authenticated staff member of any business could read, or trigger badge/milestone/voucher-awarding actions for, any other business's customer.

- `services/loyalty_group.py`'s multi-location passport aggregation computed its displayed group-tier *name* from a completely unscoped `db.loyalty_tiers` read — fixed to scope by the anchor business.

New test file: `tests/inprocess/test_loyalty_v2_tenant_isolation.py`.

## RESOLVED, post-P0.3 — `routes/reservations.py`'s waitlist API, not one of the original 34, found while enforcing Loyalty 3.0's tier perks

Discovered while wiring up the Silver+ "Priority waitlist" perk (`routes/loyalty.py`'s seed tiers list it explicitly): the whole staff-facing waitlist — `GET /waitlist`, `POST /waitlist`, `PUT /waitlist/{id}`, `POST /waitlist/{id}/seat`, `DELETE /waitlist/{id}` — had **no `Depends(get_user)` at all**, i.e. this was the true zero-credential bug class (the `bill_split.py`/`awards.py` pattern), not just a missing tenant filter on an otherwise-authenticated route. Any caller with no token could list, edit, seat, or delete any business's waitlist entries; `add_to_waitlist`'s position counter was also computed globally across every business sharing the deployment, so joining businesses would collide on/leak each other's queue-length signal even if auth were added without a tenant filter too.

Fixed with the standard pattern: `Depends(get_user)` added to all five endpoints, `get_waitlist`'s read and `add_to_waitlist`'s position-counter read scoped via `tenant_scope_filter`, `update_waitlist_entry`/`seat_waitlist_guest`/`remove_from_waitlist` each now fetch a guard document and check `tenant_owns` before mutating. `models/waitlist.py`'s `WaitlistEntry` gained a `businessId` field (stamped by `add_to_waitlist`) and a `priority: bool` field.

The Priority waitlist perk itself: `add_to_waitlist` matches the joining guest's phone against `db.customers` (scoped to the caller's business), and if found, checks whether their current `membershipTier`'s tier document (`db.loyalty_tiers`) lists "Priority waitlist" among its perks — same tier-lookup pattern already used by `routes/transactions.py`'s checkout-time tier pricing. `get_waitlist` now sorts `[("priority", -1), ("position", 1)]` so members queue ahead of non-members but still order correctly among themselves and among earlier non-members. The guest-facing, no-auth `GET /waitlist/track/{code}` (`_public_waitlist_view`) was made priority-aware and business-scoped the same way, so a guest's own "how many people are ahead of me" count agrees with staff's view.

`routes/public.py`'s `POST /public/join-waitlist` (the genuinely anonymous guest self-join form) was assessed and deliberately left unscoped, same category as `table_ordering.py`'s public endpoints: the request carries no business/table-identifying signal at all to resolve a `businessId` from, so entries it creates stay untagged — they still correctly surface to every business's staff waitlist view via `tenant_scope_filter`'s safe default (untagged docs always match), they just aren't excluded from any *other* business's view either, and they never get the priority perk (no `businessId` to look the guest's tier up against). Properly fixing this needs the same venue-resolution pattern `routes/online_orders.py`'s public storefront already uses, a real feature-level addition to this form's request shape — deferred rather than rushed. ## RESOLVED, post-P0.3 — `routes/reservations.py`'s core reservation CRUD (the entire booking system), not one of the original 34, found while building Booking 3.0's real deposit/no-show payment capture

The most severe finding of the whole Phase 3-5 pass, on par with `_stamp_new` and the `loyalty_v2.py` gap — this is the actual reservations/bookings system, carrying direct guest PII (name, phone, email, special requests, dietary/allergy notes).

**Root cause:** `models/reservation.py`'s `Reservation` model had **no `businessId` field at all**, and `create_reservation` never stamped one on the inserted document. `GET /reservations`' own `tenant_scope_filter(user.get("businessId"))` call — present and looking correct — had therefore been a **complete no-op since it was written**: with zero reservations ever tagged, the safe-default `$or` matched every reservation for every business, every time. Fixed by adding `businessId` (plus `depositSessionId`/`depositForfeited`/`depositRefunded`, needed for the payment-capture work below) to the model and stamping it at creation from `(user or {}).get("businessId")`.

**On top of that root cause, most of the single-reservation endpoints had zero auth dependency at all** (the true zero-credential bug class, same as `bill_split.py`/`awards.py`/this session's waitlist finding) — reachable with no token whatsoever: `GET /reservations/{id}`, `PUT /reservations/{id}`, `DELETE /reservations/{id}`, `POST .../seat`, `POST .../complete`, `POST .../no-show`, `GET /reservations/auto-assign/{id}`, `POST .../ai-assign-table`, `GET /reservations/guest-lookup`, `GET /reservations/guest-intel/{customer_id}`, `GET /reservations/day-counts`, `GET/POST/DELETE /reservations/blackouts`, `POST /walkins/ai-assign`, `POST /walkins/seat`. The remaining status-changing endpoints (`cancel`, `approve`, `reject`, `restore`) already required `require_owner_or_manager` but had **no ownership check** — any authenticated owner/manager of any business could cancel, approve, reject, or restore any other business's booking.

All fixed with the standard pattern: `Depends(get_user)` (or `require_owner_or_manager` for `delete`/blackout writes, matching `cancel`'s existing precedent) added everywhere, `tenant_owns` guards added to every single-resource fetch-then-mutate endpoint. `services/guest_intel.py`'s `find_customers`/`build_guest_intel` (shared by the booking-desk lookup HTTP route AND the AI phone agent's direct service-call path — `routes/phase_ef.py`'s `simulate_call`) had the identical zero-scoping gap on `db.customers`/`db.reservations`/`db.transactions` reads; both callers now thread a real `business_id` through. `routes/reservations.py`'s blackout create/delete also had zero businessId stamping, meaning two businesses blacking out the same calendar date would silently collide into one shared document (whichever wrote second won) — fixed by keying the upsert on `(date, businessId)` instead of `date` alone; `services/booking_rules_engine.py`'s existing blackout-scoping fix from earlier this session only becomes fully effective now that blackouts are actually tagged.

**New: real deposit collection + no-show payment capture** — the actual Booking 3.0 feature this was built for. `depositPaid` was previously a bare staff-ticked checkbox (`ReservationUpdate.depositPaid`) with no money ever behind it, and `mark_no_show`'s `fee` parameter was pure record-keeping. Added `POST /reservations/{id}/request-deposit`, following the exact pattern `routes/online_orders.py`'s `create_online_order_checkout` already established: its own Stripe Checkout session, a `payment_transactions` doc tagged `kind="booking_deposit"` carrying `reservationId`, and a new `_mark_reservation_deposit_paid_if_applicable(session_id)` wired into both of `routes/integrations.py`'s existing dispatch points (the webhook and the status-poll) — the same two places `_mark_online_order_paid_if_applicable`/`_finalize_pos_sale_if_applicable` already hook into. `mark_no_show` now forfeits a deposit (`depositForfeited=True`, never refunded) **only** when it was actually collected through a real session (`depositPaid` AND `depositSessionId` both set) — a bare staff-ticked flag with no session behind it correctly captures nothing, and the response says plainly which happened rather than ever claiming a fee was collected when it wasn't. `cancel_reservation`/`restore_reservation` (un-no-show) both attempt a real refund via the existing `refund_stripe_payment` helper when reversing a collected/forfeited deposit — best-effort, never blocks the status change on a failed refund.

**Honest scope limit, stated in the code and worth restating here:** NUA has no saved-card / off-session-charge capability — only Stripe's hosted Checkout, a one-time redirect flow (confirmed: the codebase uses `emergentintegrations.payments.stripe.checkout`'s `StripeCheckout`/`CheckoutSessionRequest` everywhere, never `SetupIntent` + a later off-session `PaymentIntent`). So "no-show fee capture" only works for a booking that had a deposit actually collected in advance; a walk-in/phone/online booking that never had a deposit collected still can't have a fee charged after the fact — `mark_no_show`'s `fee` param stays record-keeping-only for that case, exactly as before. Building real saved-card capture would be a materially larger, separate feature (Stripe SetupIntent + PCI-relevant card-vaulting flow), not attempted here.

Also untestable end-to-end in this sandbox: `STRIPE_API_KEY` isn't configured, so `request_deposit` always exercises its graceful `{"configured": False, "url": None}` path (same degradation `create_online_order_checkout` uses) rather than a real Checkout session — covered honestly by the test suite as exactly that: the configured-false path, not a simulated real charge.

A latent, unrelated data-quality bug surfaced by this fix (not a tenant-isolation issue): once `GET /reservations`' scope filter started actually doing something, a pre-existing reservation somewhere in the shared dev/test data had `tableNumber` stored as an int rather than a string, which `response_model=List[Reservation]`'s strict validation would reject — this bug already existed (the "no-op scope filter" behavior meant it was always in the unfiltered result set anyway) but nothing had exercised the full authenticated list response strictly enough to trip it before. Fixed with a `mode="before"` coercion in the model (some table-assignment code paths copy a floor plan table's own `number` field through verbatim, and that field isn't consistently a string across every floor plan) rather than tracking down and hand-fixing whatever wrote the bad value.

New test file: `tests/inprocess/test_reservations_tenant_isolation.py`.
